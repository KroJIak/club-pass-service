# Техническое задание

## Проект: Telegram-бот и система продажи билетов в ночной клуб

### 1. Цели проекта

Создать комплексную систему для ночного клуба, включающую:

- Telegram-бот для клиентов (покупка билетов, хранение и предъявление билетов).
- Веб-админку для менеджмента клуба (управление событиями, билетами, оплатами, статистикой).
- Инструмент/мини-приложение для персонала (staff) для сканирования билетов и контроля входа.

Система должна обеспечить:

- Удобную покупку билетов в пару шагов через Telegram с оплатой через ЮKassa.[^8_1][^8_2][^8_3]
- Генерацию и проверку уникальных билетов с QR-кодами и защитой от повторного прохода.[^8_4][^8_5][^8_6]
- Прозрачный учёт продаж и посещаемости для клуба.[^8_5][^8_7][^8_4]

***

### 2. Общая архитектура

Компоненты:

- Telegram-бот (клиентский интерфейс).
- Telegram/Web Mini App для staff (или отдельный staff-бот).[^8_6][^8_7]
- Веб-админка (SPA/классический веб-интерфейс).[^8_8][^8_9]
- Backend API (единый сервер для ботов, админки и staff-инструмента).
- База данных (PostgreSQL/MySQL или аналог).
- Интеграция с ЮKassa по API (создание платежей, обработка webhook’ов).[^8_2][^8_10][^8_1]

Основные сущности данных:

- Пользователь.
- Событие (мероприятие/вечеринка).
- Тип билета (обычный, VIP, стол и т.д.).
- Билет (состояние: создан, оплачен, активен, использован, отменён).
- Платёж (статусы, суммы, возвраты).
- Промокод (опционально).
- Логи входа/сканирования.

***

### 3. Telegram-бот для клиентов

#### 3.1. Общие требования

- Интерфейс на русском языке.
- Поддержка как команд, так и кнопок (inline и reply-клавиатура).
- Минимальное количество шагов от старта диалога до оплаты билета.[^8_7]
- Хранение контекста пользователя (незавершённые заказы, выбранные события и т.д.).


#### 3.2. Стартовый сценарий

Команда/кнопка `/start` открывает главное меню:

- «Купить билет».
- «Мои билеты».
- «Ближайшие вечеринки».
- «Инфо о клубе».
- «Поддержка».

При первом запуске:

- Запрос согласия с политикой обработки данных и правилами клуба (ссылка на документ).
- Сохранение базовых данных: Telegram ID, username, имя.


#### 3.3. Покупка билета

Поток «Купить билет»:

1. Выбор события из списка активных (дата, время, исполнители, краткое описание).
2. Выбор типа билета (обычный/VIP/стол и др.; цена, ограничения).
3. Выбор количества билетов (с проверкой лимитов).
4. (Опционально) ввод промокода.
5. Подтверждение заказа (детали: событие, тип, количество, итоговая сумма).
6. Оплата через ЮKassa в Telegram.[^8_3][^8_1][^8_2]

Требования:

- Создание платежа через API ЮKassa с указанием: суммы, описания, id пользователя, id заказа.[^8_1][^8_2]
- Обработка статуса платежа через webhook: успешен/отменён/ошибка.[^8_10][^8_1]
- В случае успеха: автоматическая генерация билетов и отправка пользователю.


#### 3.4. Генерация и выдача билета

После успешной оплаты каждый билет:

- Получает уникальный идентификатор (UUID/инкремент + контрольная часть).
- Генерируется QR-код, содержащий минимум: идентификатор билета (и/или токен, который однозначно связывается с билетом в базе).[^8_4][^8_6]
- Сохраняется в базе с привязкой к пользователю и событию, статус «активен».

Пользователю отправляется сообщение:

- Картинка QR-кода.
- Текст с данными:
    - Название клуба и события.
    - Дата и время.
    - Тип билета.
    - Уникальный код в текстовом виде (на случай проблем со сканированием).
    - Краткие правила входа (время, дресскод и т.д.).


#### 3.5. Раздел «Мои билеты»

Функционал:

- Список всех билетов пользователя:
    - Активные (ещё не использованы, не истёкли).
    - Использованные.
    - Отменённые/просроченные.
- При выборе билета:
    - Показ большого QR-кода (максимум экрана).
    - Краткая текстовая информация по событию.
- Фильтрация: «Только активные» / «Все».


#### 3.6. Ближайшие вечеринки и инфо

Раздел «Ближайшие вечеринки»:

- Список предстоящих событий с: названием, датой/временем, кратким описанием, кнопкой «Купить билет».

Раздел «Инфо о клубе»:

- Адрес, карта/ссылка, расписание работы.
- Базовые правила (возраст, фейс-контроль и т.п.).


#### 3.7. Поддержка

- Кнопка «Поддержка» с возможностью:
    - Показать контакт (телеграм/телефон/почта).
    - Опционально — отправить сообщение оператору (через отдельный админ-бот или в админку).


#### 3.8. Уведомления

Автоуведомления пользователю:

- Подтверждение заказа и оплаты.
- Напоминание о событии:
    - За 24 часа до начала.
    - За 2–3 часа до начала.
- Информационные рассылки:
    - Перенос/отмена мероприятия.
    - Важные изменения (время, место, артист).[^8_7]

### 4. Система билетов и валидации

#### 4.1. Модель билета

Поля билета (минимум):

- ID (уникальный).
- ID пользователя.
- ID события.
- Тип билета (ссылка на справочник).
- Статус:
    - `created` — создан, ожидает оплаты (если билеты создаются до подтверждения платежа).
    - `paid`/`active` — оплачен, готов к использованию.
    - `used` — использован при входе.
    - `canceled` — отменён (возврат).
    - `expired` — срок действия истёк.
- Время создания.
- Время оплаты.
- Время использования (чек-ин).
- Уникальный токен/код для QR.


#### 4.2. QR-код

Требования:

- Формат: стандартный QR-код, совместимый с камерой телефона и сканерами.[^8_6][^8_4]
- Содержимое:
    - Минимум — токен, по которому backend однозначно находит билет.
    - Не хранить в QR чувствительные данные (ФИО, контакты).
- QR генерируется на стороне сервера, файл хранится либо как изображение, либо генерируется «на лету» при выдаче.


#### 4.3. Правила валидации билета

При сканировании билета staff-инструментом backend проверяет:

- Существует ли билет с таким токеном.
- Статус:
    - Если `active` и событие актуально — разрешить вход и пометить как `used`.
    - Если `used` — показать, что билет уже проходил (с указанием времени первого использования).
    - Если `canceled`/`expired` — отказ во входе.
- Принадлежность билета к нужному событию/дате.

Результат возвращается в staff-интерфейс:

- Зелёный экран — вход разрешён (краткая информация, например тип билета).
- Красный/жёлтый — ошибка/предупреждение (указать причину).

### 5. Инструмент для персонала (staff)

Возможные варианты:

- Отдельный staff-бот в Telegram.
- Telegram Mini App для staff (WebApp с интерфейсом под мобильный).[^8_11][^8_6][^8_7]


#### 5.1. Авторизация персонала

- Вход по:
    - Логину/паролю.
    - Либо по Telegram ID, занесённому администратором как «staff».
- Разделение ролей:
    - Обычный контролёр (чек-ин).
    - Старший администратор (расширенные функции в админке, а не в staff-приложении).


#### 5.2. Основной функционал staff-интерфейса

- Экран сканирования:
    - Кнопка открыть камеру и считать QR.
    - Альтернатива — ввод кода вручную.
- После сканирования:
    - Статус: «Вход разрешён», «Билет уже использован», «Билет недействителен» и т.п.
    - Отображение: тип билета, название события, время.
- Возможность просмотра краткой сводки по текущему событию:
    - Сколько прошло людей.
    - Сколько активных билетов осталось (только read-only).


#### 5.3. Требования к скорости и надёжности

- Проверка билета и ответ — не более 1–2 секунд при нормальной нагрузке.
- Исключение двойного входа: статус `used` должен устанавливаться атомарно (мьютексы/транзакции).[^8_5][^8_4]

### 6. Веб-админка для клуба

#### 6.1. Авторизация и роли

- Авторизация по email/логину и паролю.
- Возможность сброса пароля.
- Роли:
    - Владелец/администратор (полный доступ).
    - Маркетолог/менеджер (события, билеты, рассылки).
    - Сотрудник входа (ограниченный доступ к статистике по событиям).


#### 6.2. Управление событиями

Функции:

- Создание/редактирование/удаление событий:
    - Название.
    - Описание.
    - Дата и время начала/окончания.
    - Место (адрес).
    - Лимиты по билетам (общий лимит, по типам).
    - Статус: запланировано / идёт / завершено / отменено.
- Настройка типов билетов для события:
    - Название (стандарт, VIP, стол и т.п.).
    - Цена.
    - Количество доступных билетов.
    - Ограничения (минимум/максимум в руках).


#### 6.3. Управление билетами

- Поиск билетов по: пользователю, событию, коду билета, статусу.
- Просмотр информации по билету (история: когда куплен, когда использован).
- Ручное изменение статуса в исключительных случаях (с ведением протокола: кто и когда изменил).
- Возможность выгрузки списка билетов в CSV/Excel.


#### 6.4. Интеграция с ЮKassa и платежи

- Отображение списка платежей:
    - ID платежа.
    - Пользователь.
    - Событие.
    - Сумма.
    - Статус (успешен, отклонён, в ожидании).[^8_2][^8_10][^8_1]
- Возможность открыть детали платежа.
- Отметка/ссылка на возвраты (если реализуются).


#### 6.5. Аналитика и отчётность

Минимальная аналитика:

- По событиям:
    - Количество проданных билетов (по типам).
    - Сумма выручки (по событиям и периодам).
    - Фактическое количество проходов (по данным чек-ина).[^8_4][^8_7]
- По времени:
    - Пиковые часы входа.[^8_12][^8_5]

Возможность фильтрации по периодам и выгружать отчёты.

#### 6.6. Рассылки

- Создание рассылок по базе:
    - По всем купившим билеты на конкретное событие.
    - По всем пользователям.
- Типы рассылок:
    - О переносе/отмене.
    - О специальных предложениях.
- Отправка через Telegram (бот), с логом отправки и статусами.[^8_13][^8_7]

***

### 7. Нефункциональные требования

#### 7.1. Безопасность

- Хранение токенов Telegram и ключей ЮKassa в защищённой конфигурации (переменные окружения/секреты).[^8_1][^8_2]
- Шифрование соединений (HTTPS для API и админки).
- Проверка подлинности webhook’ов ЮKassa.[^8_10][^8_1]
- Разграничение доступа по ролям в админке и staff-инструменте.
- Лимиты на количество запросов (rate limiting) для защиты от brute force/флуда.


#### 7.2. Производительность и масштабируемость

- Проектирование с учётом возможного роста нагрузки (несколько тысяч билетов на событие).[^8_5][^8_4]
- Возможность горизонтального масштабирования backend (стейт-лесс API, общая БД/кеш).


#### 7.3. Логи и мониторинг

- Логирование ключевых операций:
    - Создание/оплата заказов.
    - Генерация/использование билетов.
    - Ошибки интеграции с ЮKassa.
- Возможность просмотра логов администратором (хотя бы базовая).

***

### 8. Этапы разработки

1. **Проектирование и согласование ТЗ** (текущий документ).
2. **Проектирование БД и API**, дизайн основных экранов бота, админки и staff-инструмента.
3. **Реализация backend + интеграция с ЮKassa** (платежи, webhooks).[^8_2][^8_10][^8_1]
4. **Разработка Telegram-бота для клиентов** (MVP: покупка, билеты, «Мои билеты»).
5. **Разработка базовой админки** (события, типы билетов, базовая аналитика).
6. **Разработка инструмента для staff** (сканирование и валидация билетов).
7. **Тестирование (функциональное, нагрузочное, UX)**.
8. **Пилотный запуск на одном/нескольких событиях, сбор фидбэка**.
9. **Доработки, улучшения, расширение аналитики и маркетинговых функций**.
